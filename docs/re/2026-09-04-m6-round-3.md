## Open after round 3

### Slot 1 affliction children

**Tried.** Fixed widths 1 through 48 bytes on every slot-1 body whose child mask is only child 1. Bodies: 26,066.

**Result.** The width that ends on a known next class most often is 27, on 20,057 bodies (76.9%). Width 4 ends 15,075. Width 26 ends 14,906. No width reaches 99.9%. The reader `FUN_14694edf0` walks a list (`0x40` count, 0x28 bytes of object per step) and then calls another function. The wire size is not one constant. A running client is not required to go further; a decoder for that list is. This pass stopped after the fixed-width score.

**Later finding.** This item is settled. The affliction children are lists, not one fixed width. `2026-09-06-m6-round-4.md` item 2 ends 460,589 of 460,589 slot byte 2 bodies and 47,276 of 47,276 slot byte 3 bodies. The code is `crates/nw-messages/src/afflictions.rs`.

### Keep rule

**Tried.** In same-millisecond windows with at least 30 keys, distance from the type 1589 position to parsed entity positions. Kept samples: 8. Dropped samples: 1, and that one was farther than the entities still present.

**Why it failed.** The largest aligned window is 45 keys, below 47, so the captures do not show a window that has hit a 47 cap. Keys after the first unsized member are invisible, so 45 is a lower bound, but it is still the largest lower bound this walk produced. The client search found no 47-entity constant. Seeing who was dropped needs either a denser capture or the running server's candidate set.

## Explained difference

### Mob respawn time

**Asset.** One point spawner, from the spawners note: both cooldown fields are 360.0 s. Pak directory: 20,342 `pointspawner` slices, none stored uncompressed. `VitalsData` has no respawn-time column.

**Health drop to at most 0.5, then the same key above 5.** Drops: 5,931. Returns: 5,686. No return before the ledger ended: 245. Minimum 0 s. Maximum 1,861.265 s. Median below 1 s. Under 30 s: 5,177. From 300 s through 420 s: 19.

**Type 10 at the same key.** 39,475 cards had no position on that key within 5 s. One catacombs ledger: 365 card events, 1 card key, 7 position keys, overlap 0.

**Birth at the spawn.** 5,262 first positions, 3,066 within 20 m of a spawn, 1 paired gap. That gap is 14.869 s.

**Why this is not left open.** The capture clock and the 360 s asset do not measure the same event. The health return is a dip or a heal on a key that stays. The next-life join does not produce a 360 s cluster. A running client is not required to see that difference. A census of the other 20,342 slices would say whether 360 s is the common asset value. It would not turn the sub-second health return into that cooldown.
