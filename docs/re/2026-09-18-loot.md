## 1. Crate loot table: the variant rule

**Observed.** Generic loot crates (`LootSmallT1`, `LootMediumT1`, `LootMediumT1_Outpost`,
`LootLargeT1`, `LootLargeT3`, `LootLargeT3ElitePOI`, `MSQ_Treasure_*`, ...) have
`IsLootContainer` true and `FinalLootTable` `Empty`. The table `Empty` exists and has no
entries. The table that gives items is in `VariationData`: `LootTableComponent`, or
`LootTableID` when that is empty. It is on the variant row whose gatherable is
`GatherableEntryID`, else `GatherableEntryId`, else `Gatherable_0`.

**Observed.** The client's gather request is input 1589, bit 8. It carries:

- the gatherable CRC (CRC-32 of the lowercase `GatherableID`),
- the variant `Name`, for example `@LootContainer_AncientSmall_DisplayName`,
- a 16-byte target raw id and its facet entity.

The name of the server's 3743 answer is not always the variant name. The start-beach armour
chest was answered with `@LootContainer_AncientSmall_DisplayName`, so do not read the variant
from the answer.

**Observed.** 327 variant rows give 119 (gatherable, Name) keys, and 9 of them name more than one
table. Example: `LootLargeT1` + `@LootContainer_ArmorChestBeach_DisplayName` gives
`BeachChestMB1` / `BeachChestMB2`.

**Observed (rule).** The capital key finds the variant of a placed crate:

1. The request facet entity is the first 8 bytes of the raw id, read as a little-endian u64.
   It equals the request's facet entity field.
2. The capital key is the high 64 bits XOR the low 64 bits of the world-file capital's GUID,
   each half read big-endian, with the low 3 bits cleared.
3. The capital whose key equals `facet & !7` is the crate. Its `variant_name` is the `VariantID`.

Evidence:

- The retail start-beach chest (request raw id `1b3c94a8bff4b7dc...`, facet
  `dcb7f4bfa8943c1b`) is capital `aabcf082-9526-2edf-760b-043d3db212c4`. Its variant is
  `WeaponsChest_StarterBeach_1`, table `BeachChestMB1`. The XOR is exact.
- 26 retail requests match a capital with the low 3 bits masked. They differ from the key by 0 to
  7 in those bits.
- No two of the 268,113 open-world capitals have the same masked key.
- In all 8 named crate requests, the request's gatherable and name are the matched variant's.

**Observed.** All 157 `LootLargeT1` crates of the open world have a capital, so the three
`LootLargeT1` pairs always resolve. The crates that a slice places have no capital: 308
`LootLargeT3` and 106 `LootLargeT3ElitePOI` in the open world, plus about 125 in dungeons and
trials. The tutorial chest's facet `efa5a09f...` is not its capital's key either.

**Code.** A crate gets its capital's variant table. A crate without a capital gets the table of
its gatherable and name when only one variant has them. Otherwise it rolls its `FinalLootTable`
and the server logs "crate of an unknown variant".

## 2. Loot table conditions

**Observed.** `Conditions` is a comma list, for example `EnemyLevel,Elite`,
`MinContLevel,GreatCleave01`, `Fresh,FishRarity`. The values in build 25810808 include:

| Condition | Tables |
|---|---:|
| `EnemyLevel` | 29 |
| `EnemyLevel,Elite` | 4 |
| `Level` | 117 |
| `MinContLevel` | 3 |
| `MinPOIContLevel` | 3 |
| `GlobalMod` | 25 |
| `[LIM]...` | loot limits |

The rest are tag names.

**The level names (Observed through nwdb.info).** nwdb.info prints its loot tag restrictions
with level labels:

| Data | nwdb.info label | Meaning |
|---|---|---|
| `EnemyLevel` | "Enemy Level N+" | the killed mob's level |
| `MinContLevel` | `{!clvl}` | content level |
| `Level` | `{!plvl}` | player level |
| `MinPOIContLevel` | "POI Level N+" | the point of interest's level |

**Observed: the data is 0-based.** Each nwdb.info label is one above the data:

- Bucket tag `MinContLevel:0-18` is shown as `{!clvl}1-19`.
- Bucket tag `Level:64` (item `1hLongsword_Slots2_DropT5`) is shown as `{!plvl}65+`.
- `AzothRoll` (condition `Level`) is shown as `{!plvl}21+`.
- The threshold 0 of `CreatureLootCommonGearLeveled` (`EnemyLevel`) is shown as
  "Enemy Level 1+".

So a shown level `L` compares as `L - 1`.

**Observed.** `ExperienceData` (`XPLevels`) has `Level Number` (0-based), `XPToLevel` (the total
experience, nwdb.info `xp_total`: 150, 480, 1080, 1970, ...) and `LootTagValue`, which equals
`Level Number`. The player's `Level` value is the `LootTagValue` of the highest row whose
`XPToLevel` the player's experience reaches.

**Observed.** `MinContLevel` is not the player level, because nwdb.info shows player level as a
separate label (`{!plvl}`). The study had marked it as player level (Inferred); that is wrong.

**Inferred.**

- The content level of a kill is the enemy level. nwdb.info lists creature loot by `{!clvl}`
  ranges around the creature's level.
- `GlobalMod` rolls as a plain random roll; its bonus is Unknown.
- A level name makes the table roll that level, not a random number. This is the existing rule
  for `EnemyLevel` OR tables; the retail boar skinning gives `RawhideT1` and never `RawhideT4`.
- Any other name is a tag that the roll must hold. `CreatureLootCommon` has `Common` and
  `CreatureLootElite` has `Elite`, and those are mob `LootTags`.

**Observed (tag sources).** A roll holds a tag when the mob's `LootTags` has it, or when a table
on the roll path has that id. Of the plain bucket tags, 7,517 name a loot table, 4,894 name a mob
loot tag and 9,600 name neither (zones, weapon kinds, events). Table conditions: 30 are mob tags
and 1 is a table id.

## 3. Bucket items

**Observed.** Each bucket column has `TagsN` (a comma list) and `MatchOneN`. MatchOne is true for
2,630 items and false for 22,199.

The tag keys with a range, and how often they occur:

| Key | Uses |
|---|---:|
| `Level` | 9,887 |
| `MinContLevel` | 9,090 |
| `HWMLoot*` and `HWM*` | up to 78 each |
| `DawnLevel` | 1 |
| `EnemyLevel` | 1 |
| `level` (lower case) | 1 |

**Observed / Inferred (rules).**

- `Key:a-b` holds for a level from `a` to `b`, inclusive.
- `Key:a` holds for `a` and up: `Level:64` is `{!plvl}65+`.
- Keys compare without case.
- A key that is not a level name never holds (Unknown: `HWMLoot*`, `DawnLevel`).
- An item without tags may always drop.
- With MatchOne, one tag that holds is enough (nwdb.info `bmo`). Without it, every tag must hold.
- A bucket entry picks among the items that may drop, with equal chance. The odds columns
  (`Odds414`, ...) are not read (Unknown).

## 4. Mob loot: one bag per kill

**Observed.** Over the 695 ledgers there are 9,200 bag spawns and 13,299 mob deaths. 450 ledgers
have bags. A bag spawn is a card of asset `9844f2dec3b15bd398fa8768b5445906` sub 2. A death is
1793 `RequestDisableCollision`. Solo ledgers are close to one bag per death:

| Ledger | Bags | Deaths |
|---|---:|---:|
| `MSQ12-lv52` | 93 | 93 |
| `MSQ5-lv25` | 121 | 124 |
| `MSQ22-lv67` | 89 | 96 |

The bag lifetime scan (`bagtime`) found 7,827 bag spawn groups.

**Observed.** Own kills (hit by the own player) by mob row (`kills-by-vitals.txt`), with a bag
spawn within 1.5 s:

| Mob rows | Own kills | With a bag |
|---|---:|---:|
| `CreatureLootMaster`, `LootDropChance` 0.1 | 1,712 | 1,211 |
| `CreatureLootMaster`, chance 0.05 | 311 | 232 |
| `CreatureLootMaster`, chance 0.35 | 61 | 35 |
| `CreatureLootMaster`, chance 1 | 46 | 26 |
| `CanDropLoot` false, with a table | 74 | 51 |
| no table (`Invasion_*` and others) | about 80 | 0 |

Rows without a table and `CanDropLoot` false: 24 of 149, all near other mobs' bags.

**Conclusion.** Every kill of a mob type that has a loot table drops a bag. `LootDropChance` is
not the chance of a drop: 0.05 gave bags at 75 %, and the bag rate does not follow the chance.
`CanDropLoot` false does not stop it. What `LootDropChance` and `CanDropLoot` do is **Unknown**,
and the server reads neither. An earlier count of "no take requests" was right but proves
nothing: the take is the kind-28 interaction, not a take request.

**Observed (who may loot).** A bag is the killer's when the killer's loot tracker (982) lists it.

| Bag | Count | What happened |
|---|---:|---|
| Not tracked, never opened, life 6.0 to 6.5 s | 5,171 | |
| Not tracked, never opened, other lives | 1,160 | other players' bags in group play |
| Tracked and opened | 1,029 | |
| Tracked, not opened | 106 | removed when the player left the view; up to 631 s seen |

No 2938 answer in the captures lists a bag with 0 items. **Inferred:** a roll without items gives
a bag that nobody's tracker lists, and it fades.

**Unknown.** How a group's loot is shared. The server rolls for the killer only.

## 5. The bag on the wire

### 5.1 Spawn (kill +57 ms)

**Observed.** The bag's own group is interest 52, 5 members. Retail sends them in any order:

| Component | Class | Body | Meaning |
|---|---|---|---|
| c2 | 3139 delayed event | `01 03 59a0 00` | `totalDelayDuration` binary16 180.0 s, not completed |
| c3 | 3139 | `01 03 0000 00` | |
| c4 | 3139 | `01 03 0000 00` | |
| c0 | 10 card | `01 03` + asset `9844f2de...` + `00000002` + bag id | the card's `GdeRef` is the bag id |
| c1 | 13 position | | the corpse, with rotation |

The bag id is a v4-shaped UUID. Its facet entity is the id's first 8 bytes reversed: bag
`b88319b3219d4562...` has facet `62459d21b31983b8`.

The tutorial's asset entities 12 and 13 in `ftue-entities-25810808.json` have the same asset and
members, and are mob bags of the tutorial.

### 5.2 Loot tracker (982, own component 33)

The class is `MB::LootTrackerComponentReplicatedState`.

**Observed.** One slot. Children: `m_lootDataMap`, `m_lootCollectibles`,
`m_failedRollBonusPercent`, `m_slayerScriptDataMap`, `m_lootDivertMap`, `m_lootLimitDataMap`.
Map readers: `FUN_143728b00` (full form), `FUN_1437792a0` (delta form), element
`FUN_143728d60`.

At the kill, retail sends the full form of child 0 and child 5. At the take and at the expiry it
sends child 0 alone.

The child-0 entry is `InstancedLootData` (`FUN_14376b520`), keyed by the bag id:

| Field | Type | Value |
|---|---|---|
| `m_lootState` | u32 | 1 rolled, 2 looted |
| `m_lootType` | u32 | 1 creature |
| `m_resetTime` | u64 | unix ns |
| `m_lootedTime` | u64 | unix ns, the kill time |
| `m_requiresPrivilegedLooters` | u8 | 1 |
| `m_position` | f32 x3 | see below |
| `m_interactTag` | u32 | 0 |
| unnamed | u8 | see below |

**Observed (`m_position`).** In the reference kill, `m_position` (9858.286, 2280.0605) is the
point of a world spawn record (a `130d772d` vitals record). It is not the bag (9880.871,
2274.392); the boar spawns were at 9886 and 9898. **Inferred:** a spawn point. The server sends
the mob's spawn point.

**Observed (the unnamed byte).** It has no reflected name. In one-item bags it is 0 to 4: for gear
it follows the perk count (1-2 perks → 1, 3 → 2, 4 → 3, 5 → 4), and it is 0 for 230 of 234
items with no perks and no `ForceRarity`. For items with a `ForceRarity` the mapping is
**Unknown** (force 1 → 1, 3 → 4, 4 → 3). The server sends 0.

**Observed (times).**

- `m_resetTime - m_lootedTime` at the kill is 300 s in 781 of 782 tracked bags.
- At the take, `m_resetTime` becomes about 3 s after the bundle that carries it (2.9 to 3.0 s in
  437 of 647 looted entries). **Inferred:** take + 3 s.
- At the reset time the entry leaves the map. Reference kill: a full form with count 0, 41 ms
  after the reset.

**Observed (version).** The map versions are 34259, 34297, 34387 and 34477 at kill +57, +1322,
+4323 and +7306 ms. That is about 30 per second, a server frame number. The 982, the 2938 and
the bag's 1755 at one take all share one version.

### 5.5 Bags nobody loots

**Observed.** c3 `01 01 3d00` starts the fade 4,950 to 5,000 ms after the spawn for 4,640 of
5,908 such bags seen fading, most often at 4,966 and 4,967 ms. c3 completed comes 1.25 s later,
then the stop. The tutorial bags do the same: c3 1.25 at +5 s, completed at +6.2 s, then gone.

**Inferred.** A bag that is tracked and never opened fades when the 300 s rights end. No retail
case was seen: such bags left the view first.

## 6. Gather cancel

**Observed (scan of every accepted gather, 3743 kind 14 status 1).**

- A cancel during a gather (2473 before any 3746) got 2724 in 98 of 126 cases.
- A cancel after the gather's 3746 got 2724 in 1,561 of 3,042 cases.
- The end-to-cancel delay is the same with and without the 2724: median 12 ms.

Why retail sends no 2724 in the other cases is **Unknown**. The server sends it after every
cancel of an open-world gather.

**Observed.** After a cancel during a gather, the own gathering state (c36 81) has status 3,
amount 0.0, efficiency 0.0, `isGathering` false and the gatherable's facet. That is the same
state as at a gather's end (ledger `NH-MSQ-1`, 1789560435207). It is not the idle state 0 that
was used before.

## 7. Unknown, and where I looked

- **The variant of slice-placed crates** (`LootLargeT3`, `LootLargeT3ElitePOI`, dungeons).
  Their facet is not the capital key, so the id rule of entities inside nested slices is needed.
  The campfire work is building that reader in `crates/nw-world`. Looked: world-file capitals,
  retail crate requests, the tutorial chest.
- **What `LootDropChance`, `VitalsCategoryData.LootDropChanceOverride` and `CanDropLoot` do.**
  Looked: bag rates by chance and by `CanDropLoot` over 695 ledgers (section 4). They are not
  drop gates.
- **The content level of a gather or crate**, and the POI level the server would use.
  `TerritoryDefinition.POILevel` exists, but the server does not track the player's POI
  territory level. Looked: the `VariationData` and `GatherableData` columns (no level column),
  `TerritoryDefinition`.
- **The `GlobalMod` bonus, the bucket odds columns, `ChanceToExceedIndex`, `RollBonusSetting`,
  `GSBonus`, `HWMMult`, gear score ranges and perks.** The condition strings are not in the
  client: 0 hits for `MinContLevel`, `EnemyLevel` and `GlobalMod` in `local-data/re-sweep`.
  The roll is server code. The `[LIM]X` condition (38 tables) is Inferred from the column names
  only: the table rolls while limit `X` is below its `CountLimit`, and `TriggerLimitOnVisit`
  (`TRUE` or `1`) counts 1 on `X` per roll (`nw_content::loot`, `nw_content::loot_limits`).
- **The unnamed u8 of `InstancedLootData`** for items with a `ForceRarity`. Looked: decompile
  `FUN_143728b00`, `FUN_143728d60`, `FUN_14376b520`; 421 opened bags against master rows.
- **The u8 of a `m_lootLimitDataMap` entry** (0 in all 1,406), and the first time at the limit
  when `MaxLimitMult` is between 0 and `LimitExpireSeconds`. **Observed** (2026-09-20): child 5
  is a full list like child 0 (reader `FUN_14377a810`, element `FUN_145ce8230`): u32 CRC-32 of
  the lowercase `LootLimitID`, u64 time of the last count (the end time at the limit when
  `MaxLimitMult` >= `LimitExpireSeconds`), u64 end, u16 count, u8. Retail sends it at the kill
  with child 0 and in the login state. The server sends it (`nw_messages::loot`); 15,066 loot
  tracker members of 707 ledgers, 30 with the map, encode back byte for byte.
- **The lifetime of a tracked bag that is never opened**, and **group loot sharing**.
- **Why retail skips the 2724 after some cancels** (section 6).
- **The low 3 bits of a crate facet**, and the last 8 bytes of a node's raw id.
